2. **首页**（10s）：聚合数据、「本周推荐」——「首页一次请求拿全部数据，弱网不白屏」
3. **报名 → 签到**（25s）：详情页报名 → 扫码签到页**扫屏幕上的二维码** → 绿色成功页——「签到用的是鸿蒙 Scan Kit，相机权限系统代持，应用零权限声明」
4. **证书保存**（10s）：证书页保存到相册——「官方安全控件 SaveButton，点击即临时授权，不申请任何相册权限」
5. **互助 + 聊天**（20s）：互助详情「联系」→ 聊天气泡发消息（副号同步收）——「发布者与接单者的即时沟通，2 秒轮询，消息带已读回执」
6. **小鸿**（15s）：切小鸿 Tab 问「我的志愿时长怎么样」→ 回复带真实数据——「AI 助手由大模型驱动，服务端把用户的实时志愿数据注入上下文，所以它真的认识你」
7. **收尾**（5s）：回桌面看卡片——「鸿蒙桌面卡片 + 服务卡片刷新，Form Kit 原生实现」

## 5 分钟完整版（评委深入提问时）

在 90 秒版基础上，按模块展开：

### 动线 A：志愿活动全流程（约 90s）
- 志愿大厅：分类筛选、关键词搜索（中文编码处理）、列表按时间排序
- 活动详情：发布者卡（姓名/学院/信用分，来自后端联表）、报名、名额
- 发布活动：完整表单 → 发布 → 立即可见（「组织者自己就能发活动」）
- 扫码签到：手输兜底 + 相机扫码双路径；错码/重复签到的后端拦截

### 动线 B：互助闭环 + IM（约 90s，双设备）
- 主号发布求助 → 扣积分 → 副号接单 → 主号确认完成 → 副号积分入账 → 双方互评 → 信用分变动（「互助有信用体系约束，接单爽约扣分」）
- 聊天：求助/活动两个入口都能进对话；对方已读状态 2 秒刷新；消息中心通知角标联动
- 消息中心：四类通知会话化 + 未读角标 + 互助沟通 + 小鸿入口

### 动线 C：AI 志愿助手「小鸿」（约 60s）
- 问数据：「我的志愿时长和信用分怎么样」→ 真实姓名与数据
- 问操作：「怎么发布一条互助求助」→ 引导到功能
- 多轮上下文：追问不断片
- 话术：「服务端代理调用大模型，密钥不出服务器；把用户的实时志愿数据注入上下文，让 AI 的回答是'认识你'的，而不是通用聊天机器人」

### 动线 D：鸿蒙原生特性（约 40s）
- 桌面卡片（Form Kit）：2×4 服务卡片、定时刷新、与 App 数据联动
- 扫码（Scan Kit）、保存相册（SaveButton 安全控件）、系统分享（Share Kit）
- 长按图标/卡片点击直达

## 技术亮点话术（一句话弹药）

| 评委问 | 答 |
|---|---|
| 后端是什么？ | 自建 Spring Boot 3 + MySQL 8，12 张表、30+ 接口，部署在云服务器；签核、积分、信用分、互助闭环都是后端事务保证的 |
| 为什么轮询不用 WebSocket？ | 演示场景 2 秒轮询与推送无感差，省掉连接管理的复杂度和电量开销；接口契约不变，后续可平滑升级推送 |
| AI 怎么个性化的？ | 服务端把用户实时数据（时长/积分/信用分/待办）注入系统提示词，多轮历史持久化在数据库——AI 回答的是"这个人"的事实 |
| 密钥安全？ | 大模型 Key 只存在于服务器环境变量，App 永远接触不到；用户密码 BCrypt 加密；接口统一 JWT 鉴权 |
| 鸿蒙特性用了哪些？ | ArkTS 声明式 UI、Form Kit 桌面卡片、Scan Kit 扫码、SaveButton 安全控件、Share Kit 分享、Preferences 持久化、网络层统一封装（自动带 token、401 全局处理） |
| 最难的坑？ | 鸿蒙安全控件与权限体系（受限权限声明即拒装，改用 SaveButton 临时授权）；以及前后端字段契约一致性——都用真实编译和回归趟平了 |

## 演示保底策略

- 断网兜底：登录/首页有失败文案与 Mock 降级路径，不会白屏卡死
- 二维码提前投屏两份（主屏幕 + 备用手机），扫码失败立即切「手输签到码」——**同一接口，演示不中断**
- 双设备登录两账号提前做完：待签到报名、pending 求助、聊天会话各留一份「新鲜数据」
- 万一真机抽风：备用模拟器装同版本 HAP，所有演示动线在模拟器同样可走（扫码用手输兜底）
